## 1. Goal and scope

### 1.1 What the user gets

1. **Help for this page** in one click (or F1) from any page. It opens the guide at the top, or at the right part:
   the current PRiSM step, the simulator reference or course, the active hub member.
2. **A guide per module**, with the same nine sections everywhere. Step-by-step instructions refer to numbered call-outs
   on the screenshots. Input and result tables explain every field and every ✓ / ⚠ / ✗ verdict.
3. **Search** across every guide, the course and the field scenarios: titles, purposes, input and result labels, standards,
   keywords and synonyms (e.g. "burner" finds Flare and the clean-up exercise, "bean" finds the chokes).
4. **Getting started**: a tour of the app (sidebar, dashboard, header tools), projects and autosave, wells, units and base
   conditions, reports and the Quick Report, offline use and privacy, keyboard use, the web and iOS versions.
5. **"How do I…" tasks** (§4.8): job-to-module paths such as "design a well test spread", "unload the cushion and clean
   up", "meter gas on the orifice", "prepare the daily report".
6. **A printable User Guide**: a one- or two-page quick card per module, a chapter, or the complete book, for handouts and
   offline reading; also published at welltest.h2oil.co.uk/help/user-guide.html.
7. **A Well Test Simulator course**: exercises with goal, set-up, steps, what to watch, questions and answers, trainer notes
   and a printable trainee worksheet. Also **Field scenarios** for real jobs, starting with unloading the cushion to the
   burner boom or a production line.

### 1.2 Out of scope

- Live classes, videos, or animated walkthroughs that drive the page (a guided "tour mode" is a v2 candidate).
- Languages other than UK English (Q8).
- Changing calculator behaviour (except WP-SIM), or rewriting existing Notes and info-bar text.
- Reviving the generic tooltip MANIFEST in 28-help-tooltips.js (a separate clean-up task).
- Help for internal routes: `gaevents` (no sidebar row). The `dca` and `pta` aliases share the `prism` guide.

## 2. In-app Help centre (WP-H)

```js

  key: 'help', title: 'Help & User Guide', navTitle: 'Help & Guide',
  sub: 'How to use each module, the simulator course and field scenarios',
  group: 'Overview', icon: '?', desc: 'Guides, screenshots, training course and printable user guide',
  render: function (body) { WTS_help.mount(body); }
};
```

- `__NAV_ORDER`: insert `'help'` after `'home'` (host edit H1). Overview: home, help, clientinfo, wells, privacy = 5 rows.
- The dashboard tile comes from the registry automatically.
- `render()` does not call a `calc*` function; there is nothing to calculate. The registry contract and the existing smoke
  check (key, render, title, group only) already allow this; the smoke test is not changed for it (§7.6).

### 2.2 Entry points (host edits, written by WP-H as `help-host-patch.js`, applied by WP-I)

The edits below are not made by hand in a help branch. WP-H writes them as `prism-build/help-host-patch.js`: a node script
that exports `patch(html) → html` and has a CLI. Each edit is anchored on a stable text, guarded by a done marker
(`/* help-host-patch:H1 */` …) so a second run changes nothing, and keeps the file's line endings. The help-page test
applies `patch()` in memory to the sources build and loads the result with `loadApp({html})`. WP-I runs the CLI once on the
merged `Dev`, then rebuilds (§9). Line numbers below are v3.3 hints only; the script anchors on text.

**Header button on phones.** At 390 px the header already holds the hub tabs, the well menu and the tools. `#pgHelpBtn` is
a 28 px circle on the web and ≥ 44×44 px under `html.ios-app` (rule in `ios-styles.css`). A layout assertion
(`ux-layout-check.js` at 390 px, and `gui-sweep.js --mobile` after the sim-equip merge) checks on the five longest page
titles that the button is visible, the title does not wrap to a third line, and there is no horizontal scroll.

Everything else is in `49-calc-help.js`. The click handler on `#pgHelpBtn` and the **F1** handler are registered once, on
`document` (`keydown`, `preventDefault` on F1 only). They call `WTS_help.open(currentRoute, ctx)`, where `ctx` is:
- `{section: 'step-' + PRiSM_currentStep()}` on `prism`;
- `{part: 'reference'}` on `wts`;
- the active member on a hub page.

`WTS_help.open` stores the target in memory and calls `nav('help')`. The page then shows that guide with a
**← Back to <page>** button, which returns to the route and puts focus back on `#pgHelpBtn`. No timers and no polling.

- **Contents** follows the sidebar: groups and rows are read from the live sidebar DOM (`.nav-group`, `.nav-btn[data-p]`,

### 2.4 Search

- The index is built synchronously on the first search (66 guides, about 400 kB: well under 50 ms). It covers the title,
  navTitle, purpose, keywords, section headings, input and result labels, standards, exercise titles and the
  field-scenario titles.
- The index also covers the `tasks` titles and step lines (§4.8); a task hit ranks above a module-body hit.
- Scoring: exact title 10, task title 8, title word 6, keyword or synonym 5, label 3, standard 3, body 1. Ties keep
  sidebar order.
  At most 20 results, each showing the module, the section and a 120-character snippet with the hits in `<mark>`
  (the snippet is escaped first).
- Synonyms (in 49-calc-help.js, generic oilfield terms only): burner↔flare, bean↔choke, gauge tank↔tank,
  cushion↔clean-up/unload, SITHP↔shut-in pressure, BS&W↔water cut, PSV↔relief, GOR, AOF, IPR …, and the pressure terms
  of the field question: "production pressure", "FWHP", "FTHP", "flowing pressure", "tubing pressure", "line pressure",
  "export pressure", "back pressure" all find FS-1/FS-2 and their "which pressure goes where" table (§6.2), plus the
  `wts` reference inputs part.
- `#help_q` is `type="search"` with `data-no-persist`. Keys: **/** focuses it (only when focus is not in a text control),
  ↑/↓ move through the results, Enter opens one, Esc clears. Results are a `role="listbox"`, and the input has
  `aria-controls` and `aria-activedescendant`.

### 2.5 Keyboard and accessibility

- Every control is a `<button>` or a link with a visible focus ring (50-a11y styles). Headings run h2 (guide) → h3
  (section); each section has the id `help-<route>-<section>`.
- Opening a guide moves focus to its h2. **Back** returns focus to the opener.
- Images have alt text (≤ 200 characters) and a visible caption. Call-out numbers in the steps (written ①②③ in content)
  match the numbers drawn on the screenshot, and every step also stands alone as text. The renderer draws them as a CSS
  circle `.help-co` with a plain digit, the same shape the shots tool draws (§3.3), so no font needs the ①…⑨ glyphs.
- The image lightbox (click or Enter on a screenshot) is a `<dialog>` opened with `showModal()`: focus stays inside, Esc and
  the ✕ button close it, and focus returns to the image.
- F1 opens help; `?` stays the simulator's own keyboard sheet. Help adds no other global shortcut.
- Contrast follows 50-a11y. The decimal-comma option affects unit tokens (§4.4).

### 2.6 Phones (390 px) and iOS

- Below 700 px the Contents column becomes a `<details>` "Contents" at the top, and the search bar is `position: sticky`.
- Screenshots use `<picture>`: the phone image for `(max-width: 600px)`, the desktop image otherwise. Images are
  `max-width:100%`, and tables scroll inside their own `.help-tbl` wrapper (no page-wide horizontal scroll).
- **Call-outs on phones:** a phone image gets its call-outs drawn from the same selectors in the phone view (§3.3). Where a
  crop has no phone image, the desktop crop is shown with a "Select to enlarge" hint (it opens the lightbox), never a phone
  image without the call-outs the steps refer to.
- `ios-webkit-check.js` opens one guide with call-outs (`orifice`) at 390 px and checks that the images, call-outs and
  lightbox lay out without horizontal scroll.
- The lightbox is the only overlay. It needs the `html.ios-app` safe-area rule in `ios-app/ios-additions/ios-styles.css`,
  with block layout so the bottom padding scrolls:
  `html.ios-app .help-lb { padding: max(12px, calc(8px + env(safe-area-inset-top))) max(12px, calc(8px + env(safe-area-inset-right))) max(12px, calc(8px + env(safe-area-inset-bottom))) max(12px, calc(8px + env(safe-area-inset-left))); }`
- The sticky search bar gets `html.ios-app .help-bar { top: env(safe-area-inset-top, 0) }` only if the app header is not
  already under the safe area (WP-H checks this in the iOS WebKit layout check, `prism-build/ios-webkit-check.js`).
- Form controls are ≥ 16 px under `html.ios-app` (existing global rule), so the search input does not zoom.

### 2.8 Rendering safety

- All content text is escaped (`_rEsc` pattern) before the markup subset is applied. Raw `<`, `>` and `&` in content are
  rejected by the test, so nothing in content can become HTML.
- Images come only from `help/img/` paths listed in the manifest; the renderer builds the `src` from the route and shot id,
  never from free text.
- Help reads no localStorage value into HTML except the two prefs below (validated against known routes).

### 2.9 Stored state

- `wtspref_help_last`: the last guide opened (a route key, validated). `wtspref_help_offline`: set after the user downloads
  images for offline use.
- These keys do not start with `wts_` or `h2oil_`, so they are not in project files. Help writes nothing to `wts_page_help`;
  the help-page test checks this.

### 2.10 Offline images (web)

The service worker caches same-origin images (cache-first, keyed by the full href) once fetched. The landing view has a
**Download screenshots for offline use (≈ N MB)** button. It fetches every manifest entry once, in sequence, with a progress
line, and sets `wtspref_help_offline`. This is a user action, with no timers. No precache list is added.

**`sw.js` changes (owned by WP-S).** Today `route()` treats any `*.html` under the scope as kind `shell` (sw.js ~l.74–75), and
the offline fallback (~l.130–132) serves the first cached `.html` for any shell URL that was never cached. Without a change:
(1) `help/user-guide.html` would enter the shell cache, and its background refresh would call `notify()` and show the app's
update banner; (2) an offline user could be served the guide in place of the app; (3) a screenshot seen once would be kept
forever after a re-shoot. So:
- paths under `help/` are routed as `static` (the images, and `help/*.html` added to the static match for that folder only),
  and `shell` is limited to `SHELL_PAGES` plus the scope root and its `index.html` alias (both serve the app page, as
  before; `SHELL_ALIASES` in `sw.js`);
- `help/` entries are stored in their own cache, `wts-help-v1` (not the shell cache). The Download-for-offline action
  (WP-H) posts `{type: 'WTS_HELP_PRUNE', keep: [the current image and guide URLs]}` to the worker after its fetches, and
  every other `help/` entry is deleted, so superseded screenshots and guide versions do not accumulate;
- the offline fallback picks only from `SHELL_PAGES`;
- the renderer adds `?v=<first 8 hex of sha256>` (from the manifest) to every image `src`, and every link to the guide
  carries `?v=<RELEASE_NOTES[0].ver>`; static entries are cache-first keyed by the full href, so a new hash or version is a
  new entry and the guide never raises the update banner.
- Routing cases (a help image, `help/user-guide.html`, the app page, an uncached shell URL offline) are added to the
  existing `tests/sw-offline.test.js`.

### 3.3 Recipes (declared beside the guide, run by the tool)

Each guide's `shots` array holds the recipes. Writers own them; WP-S owns the interpreter.

```js
shots: [
  { id: 'view', view: 'both', alt: 'Orifice Plate Selection page with default inputs', caption: 'The page as it opens' },
  { id: 'res', view: 'desktop', target: '#or_res', alt: 'Results box with the selected bore and the DP band',
    caption: 'Results: bore, β, DP at minimum and maximum rate',
    setup: [ { set: { '#or_qmax': '12' } }, { waitFor: '#or_res .rbox' } ],
    callouts: [ { sel: '#or_res .rrow:nth-child(1)', n: 1 }, { sel: '#or_res .verdict', n: 2 } ] }
]
```

- **Ops:**
  - `set` {selector: value}: sets the value, then fires input and change.
  - `select` {selector: optionValue}.
  - `click` selector; `press` key; `hover` selector; `scroll` selector.
  - `waitFor` selector (timeout 15 s); `waitEvent` name (e.g. `prism:fit-updated`, timeout 120 s).
  - `action` name with `args`: a named routine defined in `help-shots.js`. Content never holds code.
- **Named actions (initial set):**
  - `prismAnalyse`: ▶ Analyse, then wait for `prism:fit-updated`.
  - `prismStep` n.
  - `buildupDemo` kind.
  - `modbusSimDemo`.
  - `wellosDemo`.
  - `simReset` 'steady'|'empty'.
  - `simRun` {speed, simSeconds}: play, run, then pause, using only the public `WTS_live` / `WTS_sim` API.
  - `simFault` name.
  - `simRigup` {item: on|off}.
  - `simCard` tag.
  - `simMenu` name.
  - `simView` '2d'|'3d'.
  - `quickReport` template.
  - `metric` true|false.

  Writers ask WP-S for new actions.
- **Call-outs:** before the shot, the tool injects a temporary overlay of numbered markers next to each `sel`, and
  removes it afterwards. Each marker is a CSS circle (22 px, high-contrast amber on dark, `border-radius:50%`) holding a
  plain ASCII digit 1–9, not a ①…⑨ glyph, so it does not depend on the container fonts. The step text uses the same
  numbers. Call-outs are declared once per shot and drawn **in every view** the shot has, from the same selectors in that
  view's layout; the shot **fails** if a call-out selector is not visible in a view it is drawn on.
- **Target:** `'viewport'` (the visible viewport, `fullPage:false`) or a selector. The element shot gets 8 px of padding,
  clipped to the viewport.
- **Masking:** before every shot the tool hides changing chrome with a temporary `visibility:hidden` style: the version label
  (`#appVersionLabel`) and the simulator's DOM clock text. Recipes may add `mask: [sel, …]`; a page can mark a field
  `data-help-mask`. Report dates and "today" fields are **not** masked by selector: the fixed `Date` (§3.4) makes them read
  2 November 2026 in every run, and they are part of what the guide describes. The `SIM T+…` text drawn into the 2D canvas
  cannot be hidden by CSS; it is deterministic on the paused fake clock.
- **Crop:** a call-out marker on the target's edge grows the crop to hold it (within the viewport); a call-out on an element
  outside the target, or a marker outside the final crop, fails the shot. A target larger than the viewport is cut at the
  viewport edge with a `[warn]` (`--strict` makes it a failure): target a smaller element, such as one `.rbox`.

### 3.5 Tool (`prism-build/help-shots.js`)

```
node prism-build/help-shots.js --all                    # every guide, course, scenarios, start
node prism-build/help-shots.js --route orifice,wts      # some routes
node prism-build/help-shots.js --changed                # recipeHash or structural fingerprint differs (below)
node prism-build/help-shots.js --check                  # no browser: content ↔ manifest ↔ files ↔ 48-calc-help-manifest.js,
                                                        #   plus fingerprints from the jsdom harness (used by the test)
  options: --phone-only, --desktop-only, --workers 4, --verbose, --keep-png <dir>
```

- **Shared helpers:** `gui-sweep.js` is **not** edited by WP-S: the `sim-equip` plan gives that file to its WP-L, and the two
  branches would edit it in parallel. WP-S copies the few helpers it needs (the static http server, the library routes and
  request stubs, `freshSession`, `navTo`) into a new `prism-build/pw-session.js`, which `help-shots.js` requires. After the
  `sim-equip` merge, a separate clean-up (coordinated with WP-L) may make the sweep require `pw-session.js` too, and add the
  export guard there.
- **Stale detection (structural fingerprint):** for every shot the manifest holds `fp`, a hash of the target element's
  visible text, ids and class tree, and `fpBox`, its bounding-box size, both computed in the jsdom harness
  (`tests/_harness.js`, no browser) after the recipe's `set` / `select` / `click` ops (named actions that need a browser
  mark the shot `fp: "browser"` and are checked only by `recipeHash`). `--check` (and so the test) flags a shot **stale**
  when its fingerprint or recipeHash differs, independent of the app version; a version bump alone marks nothing.
  `--changed` re-captures only the flagged shots, and a new file is written only when the pixel difference against the
  committed image passes a threshold (mean absolute difference > 0.5 % or any 16×16 block > 8 %); otherwise only the
  manifest's `fp` is refreshed. So a release with no UI change adds no image bytes to git, and a mid-release label or CSS
  change is caught.
- `--check` validates files, sizes, dimensions, caps, alt texts and fingerprints. It never compares bytes against a fresh
  render (that needs the container).
- **Encoding:** a PNG from `page.screenshot` / `locator.screenshot` is drawn on a canvas in a blank page and encoded with
  `toDataURL('image/webp', q)`. q is 0.80 for desktop and 0.75 for phone. If a file is over its cap, retry at q 0.65, then
  downscale by 0.85 (at most twice). If it is still over, the run fails for that shot.
- **Output:** the tool writes `help/img/**` and updates `manifest.json`, sorted, with stable JSON and no capture time
  inside the image. Orphan files (in no recipe) are reported; they are deleted with `--prune`.
- **Exit codes:** 0 for ok, 1 for a failed shot or cap, 2 for a tool error. `[skip]` (exit 0) without Playwright.
- **Run time** is about 10–15 minutes with 4 workers. PRiSM fits and simulator runs dominate.

### 4.5 Writing rules (for every writer)

- Write for international field crews, many of whom read English as a second language: short sentences (the test warns
  above 25 words), the action first, the control's exact label in bold. Write in UK English ("colour", "metre"), as the
  app does.
- Use "select" for buttons, menus and switches ("Select **Reset**"), not "click" or "tap", so the text works with a mouse,
  a finger and a keyboard. Mention F1 and other keys only in the keyboard appendix and Getting started §9.
- Oilfield shorthand is used consistently and explained once: the **first use of each glossary term in a guide** is a
  glossary link (`[[glossary#bean|bean]]`); the test checks it against the glossary keys (bean, BS&W, SITHP, FWHP, GOR,
  cushion, …).
- Explain every verdict on the page and what to do about it.
- Every number in a worked example comes from running the page or engine (`example.check`), not from memory.
- Standards: designation and topic only, e.g. "API RP 14E (erosional velocity)". No clause text is copied.
- Neutral names only. Never name another company, product, vendor or website, or describe one ("like the X software").
  Never write the forbidden product name in CLAUDE.md. Platform words: only those in the allowed list (Conventions, Q20);
  browsers are never named.
- Do not promise features. Say "not modelled" plainly. Future work is not mentioned, except the WP-SIM switch in FS-1/FS-2,
  which is selected by feature detection, so the text only ever describes what is installed.
- Link to the existing Notes, ⓘ pop-ups and setup-guide card on the page; do not copy them.

## 6. Well Test Simulator course and field scenarios (WP-T)

### 6.1 The key idea (first page of the course and of the `wts` reference)

The simulator is a **dynamic replay around a steady design calculation**. The page form feeds `calcWTS`. That calculation
walks WH → SDV → choke, and back-walks the choke outlet pressure from the separator **Operating Pressure**. That gives the
choke regime, capacity, J-T cooling, node temperatures, hydrate margins and velocities.
- **Gas, oil and water rates are inputs.** The bean is checked against the **gas** rate. If it is too small, all three rates
  are cut by the same factor to the choke capacity and CK-101 raises CHOKE_LIMIT. The bean never limits a liquid-only rate.
- Form changes apply live, without a reset, and are logged in Events.
- So the simulator is for practising **operation of the surface spread**: line-ups, levels, pressures, alarms, ESD, tank
  gauging, upsets and hydrates. It is not for predicting what a well will make on a bean.

### 6.2 Field scenarios (answers for real jobs)

All numbers in this section come from running the v3.3 `calcWTS` in the harness with the inputs stated (script kept in
the session scratchpad, `help/fs1-run.js`). The live-simulator figures are derived from `pDown()` and the choke-outlet
formula (Appendix B) and stay `manual` until Round 7 is in the harness. Control labels are as on the page: the separator
pressure is **Operating Pressure** in the **Separator** card; the surge-tank pressure is **Surge Tank Pressure** in the
**Dynamic Simulation** card.

**Which pressure goes where (opens FS-1 and FS-2; also in the `wts` reference inputs part).** Well testers use
"production pressure" for two different things, so the table covers both readings.

| The pressure you have | Where it goes | Rig-up | Scenario |
|---|---|---|---|
| Flowing wellhead / tubing pressure (FWHP, FTHP, "flowing pressure") | **Wellhead Pressure** (`wts_Pwh`), never the separator pressure | any | all |
| Production / export line pressure (the header the well flows into) | separator **Operating Pressure** (`wts_Psep`), plus the line loss to the header | **V-101 in** only | FS-2 |
| Burner boom (cushion or clean-up straight to the burner) | leave the line pressure out: **V-101 out**, separator **Operating Pressure** set low ({{15|pressureG}}), **Surge Tank Pressure** ≤ Operating Pressure − 10 (e.g. {{5|pressureG}}) | **V-101 out** | FS-1 |

| What the separator **Operating Pressure** controls | V-101 in | V-101 out (bypass to the burner) |
|---|---|---|
| Live model: PCV-101 set point, separator pressure | yes | no (PCV-101 held shut) |
| Live model: separator alarms and relief (PAH, PSHH, PAL, PSV/MAWP) | derived from it | quiet |
| Live model: choke outlet pressure | separator pressure + line losses | 5 psig burner header + Sep→Flare loss + (steady choke outlet − Operating Pressure) |
| Steady check (`calcWTS`): choke regime, capacity, J-T cooling, node temperatures, hydrate margins, line velocities | yes | **yes, still** — so it must be set near the burner back pressure |
| Surge Tank Pressure limit (clamped to ≤ min(30, Operating Pressure − 10)) | yes | **yes, still** |

**FS-1 Unloading the completion cushion straight to the burner boom.**
- *Today (v3.3.x):*
  1. **Rig-up:** switch **V-101 Test separator** out. The card note reads "whole well stream goes straight to the flare /
     burner (clean-up)". FS-401 stays in (it cannot be taken out at the same time).
  2. **Pressures:** set separator **Operating Pressure** to {{15|pressureG}} (roughly the burner-line back pressure; up to
     {{20|pressureG}} is fine) and **Surge Tank Pressure** to {{5|pressureG}} (it must be at least 10 psi below the Operating
     Pressure). If you leave Surge Tank Pressure at its default {{25|pressureG}}, the page shows "⚠ Surge tank pressure too
     close to separator pressure — liquids cannot dump" and uses {{5|pressureG}} anyway. With V-101 out no liquid reaches the
     tanks, so that warning is harmless here, but set {{5|pressureG}} so the page is clean. **Do not enter the production
     pressure, and do not enter the flowing wellhead pressure, in Operating Pressure.**
  3. **Unload phase** (live input changes, no Reset): **Gas Rate** {{0.3|gasRate}}, **Condensate / Oil** 0,
     **Water Rate** = the unload rate (e.g. {{2400|liquidRate}}), **Wellhead Pressure** = the flowing WHP while unloading (e.g.
     {{500|pressureG}}), bean {{32|count}}/64. With these inputs the steady check gives: regime **Critical**
     (P2/P1 0.068), maximum rate at this ratio {{1.78|gasRate}}, so **no CHOKE_LIMIT**, choke downstream pressure
     {{21|pressureG}} on the page, and no warnings. In the live view, the choke outlet with V-101 out is about {{10|pressureG}}
     (5 psig + Sep→Flare loss ≈ 0 + (20.5 − 15)).
  4. Run at ×60 until **Cum water** reaches the cushion volume. The time to unload is **cushion volume ÷ the rate actually
     flowing**: 150 bbl at 2,400 BPD is about 1.5 h.
  5. **If CK-101 shows CHOKE_LIMIT**, raise the bean or lower the unload rate until it clears; the time to unload is then
     the cushion volume ÷ the rate actually flowing (the alarm cuts all three rates by the same factor). With the inputs
     above, the alarm appears when Wellhead Pressure falls to about {{60|pressureG}} (capacity {{0.25|gasRate}} on a
     32/64 bean); it is clear at {{100|pressureG}} ({{0.39|gasRate}}).
  6. **Breakthrough:** raise Gas, Oil and Wellhead Pressure to the expected values and lower Water to the formation rate.
     Example: {{5|gasRate}}, {{500|liquidRate}} oil, {{300|liquidRate}} water, WHP {{2000|pressureG}}: Critical, capacity
     {{7.21|gasRate}}, choke downstream {{24|pressureG}}, no warnings. At the full design rate
     ({{10|gasRate}}) with Operating Pressure still {{15|pressureG}}, the page shows ✗ "Heater→Sep: Velocity 287 ft/s
     EXCEEDS erosional limit 240 ft/s" and two ⚠ velocity warnings: that is the cue to go through the separator.
  7. **When clean, before putting V-101 back in:** set separator **Operating Pressure** back to the test pressure (e.g.
     {{150|pressureG}}) and **Surge Tank Pressure** back to {{25|pressureG}}, let the set points ramp and the readings
     stabilise, then switch V-101 in and start the test. Otherwise the main test runs at {{15|pressureG}} and every separator
     alarm limit is wrong.
  - **Limits (say plainly):** the cushion itself is not modelled (fresh-water density, no cushion tail, and WHP does not
    rise by itself as the column unloads); the choke capacity check uses the **gas** rate only, so the bean never limits the
    liquid rate.
  - **Checks:** `example.check` of kind `page` on route `wts`: (a) the step-3 inputs with Surge Tank Pressure
    {{25|pressureG}} → `expectText` the surge warning above, `WTS_state.flow.choke.Pout` = 20.5, `regime` 'Critical',
    `flowLimited` false, `QmaxMMscfd` = 1.78 (tol 0.02); (b) the same with {{5|pressureG}} → `absentText` the warning;
    (c) WHP 60 → `flowLimited` true, `QmaxMMscfd` 0.25; (d) the step-6 inputs → `Pout` 24.1, no warnings; (e) defaults →
    `Pout` 157.7. The live figures (about 10 and 14 psig) stay `manual` until Round 7 is in the harness (§7.5). So the guide
    fails as soon as the warning text or a quoted number changes.
- *After WP-SIM:* choose **Bypass destination = Burner / flare line** and run **Scenarios → Cushion unload** with the
  cushion volume, SG and unload rate. The steady choke check then uses the real back pressure automatically, and steps 2 and
  7 are no longer needed.

**FS-2 Flowing straight to a production line.**
- *Today:*
  - **What is valid:** keep V-101 in and set separator **Operating Pressure = production-line pressure** (plus the header
    line loss). The flowing wellhead pressure still goes in **Wellhead Pressure**. This is right for the choke: ΔP, regime,
    capacity, J-T, hydrate margins and the upstream velocities. In critical flow (P2/P1 below about 0.55) the rate does not
    depend on the back pressure at all. The default spread shows it: at {{150|pressureG}} the choke downstream pressure is
    {{158|pressureG}}, P2/P1 0.057, Critical (page check, as FS-1 (e)).
  - **Closest rig-up:** V-101 in at that pressure, **FS-401 out** (gas to the export line), **T-201 and T-301 out** (liquids
    straight to the export line).
  - **What it gets wrong:**
    - it still separates and meters the stream (meters, GOR, BS&W);
    - PCV-101 holds the pressure constant, unlike a real header;
    - the gas path downstream of PCV-101 is still modelled at the 5 psig header;
    - **the separator alarm and relief set points are derived from the set point** (PSHH = SP + max(20 % of SP, 25 psi),
      PAH = SP + max(10 %, 15 psi), PAL = SP − max(20 %, 20 psi), PSV / MAWP = max(1440, 1.25 × PSHH) psig), so they follow
      the line pressure and do **not** represent the real header protection;
    - the surge limit moves with the set point.
  - **Not possible today:** "no separator, straight to the production line". The rig-up forces the flare back in.
- *After WP-SIM:* V-101 out with **Bypass destination = Production line at P psig**. FS-401 may then be out, and the
  totals go to "to production line".

**FS-3 Clean-up with sand: the desander upstream of the choke.** This uses the DS-101 rig-up item, the sand-flow-back
scenario and the dump sequence, as shipped in v3.3.1. WP-T writes it after re-checking against the merged code.

**FS-4 Cold start-up and hydrates.** Low WHT, heater bypassed, then the heater in. It links to [[hydrate]] and [[cheminj]].

### 8.1 Bypass destination (V-101 out)

- **Inputs** (Dynamic Simulation card, host):
  - "With V-101 out, well stream to": `wts_bypass_dest` = Burner / flare line (default) | Production line;
  - "Production line pressure": `wts_bypass_P`, pressure category, default {{150|pressureG}}, range 0–1440;
  - both passed through `flow.sim` (`flowDerived`) as `cfg.sep.bypass = { dest: 'flare'|'line', P_psig }`.
- **Engine** (31-wts-sim.js):
  - `pDown()`: when V-101 is out, `P0 = dest === 'line' ? P_psig : cfg.sep.pcv.P2_psig` and it returns
    `P0 + SS[4].dP · fg²`.
  - `normRigup()`: V-101 out **and** FS-401 out is allowed when `dest === 'line'`, with the note "whole stream to the
    production line at P psig".
  - Accounting (`substep()`, the bypass split): with `dest === 'line'`, the bypassed gas, oil and water go to the new sinks
    `cum.lineGas / lineOil / lineWater` (added to `massErr()`), not to flared and burnt.
  - `refresh()`: flame 0, and the flare node is relabelled to the line pressure.
  - `snap.bypass = { dest, P_psig }`; `WTS_sim.features.bypassDest = true`.
- **Host `calcWTS`:**
  - It reads the rig-up (`wts_sim_rigup`). With V-101 out, it back-walks the choke outlet from the destination pressure (the
    line P, or 5 psig + the Sep→Flare loss for the burner) instead of `wts_Psep`.
  - Segment 5 is computed as multiphase (the whole stream).
  - The fixed 5 psi heater drop is skipped when H-101 is out.
  - A ⚠ warning appears when the destination pressure makes the choke subcritical.
  - The surge set-point limit stays tied to Psep only when V-101 is in.
  - This fixes the FS-1 catch.
- **HMI** (38-wts-live.js): the rig-up note, the HUD totals "To production line", and the flare card label.

### 8.2 Cushion-unload scenario

- **Configuration:** `cfg.cushion = { V_bbl: 150, SG: 1.00, q_bpd: 2400, tbgCap_bblft: 0.00579, gasFrac: 0.05,
  tailTau_s: 1800, breakTau_s: 600 }`.
  - Three inputs: cushion volume, cushion SG (0.80–1.50), unload rate.
  - The tubing capacity defaults from 2-7/8″ 6.5 lb/ft (2.441″ ID: 2.441²/1029.4 = 0.00579 bbl/ft), editable.
  - `sim.startCushion(o)` / `sim.stopCushion()` through the existing mutator path. A Scenarios menu item is added:
    "Cushion unload (clean-up)".
- **State:** `X.Vc` (bbl left) and `X.tBreak`. Phases are unloading → breakthrough → done.
  - While unloading, the rate ramp targets in `substep()` are replaced: water = q_c, gas = gasFrac·qg, oil 0, and
    `X.Vc −= q_c·h`.
  - At `X.Vc ≤ 0`: a `breakthrough` event, then a blend to the formation rates (breakTau). A cushion tail
    `q_c·exp(−t/tailTau)` is added on top of the formation water.
- **WHP target** (the WHP ramp in `substep()`): `Pwh_ss − 0.433·SG·(X.Vc / tbgCap)`, bounded ≥ `pDown() + 50`, so WHP rises as the column
  unloads.
- **Cushion liquid** uses SG for the line density and the LCV-101 dump. `cum.cushionOut` counts it by destination
  (burner, line, or separator water leg and tanks).
- **Output:** `snap.cushion = { on, phase, Vleft_bbl, recovered_bbl, tBreak }`, a history key `cushionLeft`, and a HUD line
  "Cushion recovered x / V bbl". `WTS_sim.features.cushion = true`.
- Default **off**: with no cushion started, results are bit-identical to v3.3.1.
