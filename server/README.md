# server/ — web accounts and cloud projects API

The functions-only site of docs/ACCOUNTS-PLAN.md (§2, §3, §13). It is never published as static content and never copied to
`ios-app/www`. Configuration comes only from environment variables (`core/config.js`; secrets never in the repository).
A missing or unknown `WTS_ENV` is treated as `production` (proxy signature required, production host only); `dev.js` and
the tests set it explicitly. Without a database, keys or a blob store every data route answers `503 paused`, so a site with
no server configured behaves exactly as v3.4 (the page's cloud UI stays hidden unless the server answers).

## Hosting (v4.0: Netlify)

The functions-only site runs on Netlify as a **second site** of the same team as the static site, with base directory
`server` (`netlify.toml` here; the repository root carries no configuration for it). Owner steps: `RUNBOOK.md`, "Switch it on
with Netlify". The team must be on a **credit-based plan** (Netlify Database exists only there; a legacy plan has to switch its
billing first); the credit-based **Pro** plan gives the London function region and 30-day database backups.

### Live site, same-site mode (owner decision 2026-11-09; RUNBOOK §3L)

The API now runs **on the live site itself** (welltest.h2oil.co.uk, Free plan) instead of a second functions-only site:
`WTS_SITE_MODE=same` (`core/config.js`) turns the proxy-signature check off (there is no proxy), demands the exact production
Host header in every `WTS_ENV` (the platform address and previews answer 404; no forwarding header is trusted) and reads the
client address only from `x-nf-client-connection-ip`; every other control is unchanged. Missing or unknown = `separate` (the
signature is required), and the separate-site layout and tests stay as they were. `node site/build-live.js --out <dir>` builds
the one upload folder (static allow-list under `public/`, `netlify.toml` = `site/netlify-check.js LIVE_TOML` whose build command
`node site/netlify-check.js --live` refuses a broken bundle, the pinned runtime dependencies, the functions without a region pin
— layout `live-inline` by default: `api` on `/api/v1/*` only plus the three scheduled functions running their jobs in place —
the platform migrations and the server code; nothing else); `--check --dir <dir>` lists it and fails on anything outside the
allow-list or any secret-looking file. On the Free plan the database is in the platform's default region (United States, Ohio)
for good; Blobs stay in `eu-central-1`. `WTS_INVITE_BOOTSTRAP` (addresses, run time) stands in for the database allow-list so
the owner can be invited without a direct database connection. `ops/remote-smoke.js` has a same-site mode (`WTS_SMOKE_MODE=same`,
no signature, `WTS_SMOKE_ALT_BASE` = the platform address that must answer 404). Tests: `test/same-site.test.js`.

### Platform migrations

Netlify applies `server/netlify/database/migrations/<digits>_<slug>.sql` itself at each **production** deploy, in lexicographic
order, records what it applied, and blocks the publish when one fails. An applied file must never change or disappear, and DDL
is never applied to the platform database through a direct connection (no agent, no script, no `psql`).

- `db/migrations/NNN-*.sql` stay the source of truth. `node db/platform-migrations.js --write` generates the platform folder;
  `--check` (and `test/platform-migrations.test.js`) fails when the two drift. `--write` refuses to change or remove an existing
  file (`--force` only before a backend's first deploy). Never edit the generated files.
- Names: `NNN-slug.sql` → `NNN0_slug.sql`; slots ending in a non-zero digit are the platform's own steps, so a later source file
  (`060-x.sql` → `0600_x.sql`) always sorts after them: `0000_platform_roles.sql` (capability check, the wts_* roles, their grants
  to the login — what `migrate.js --platform` does first — and `public.wts_schema_migrations`, marked so `migrate.js` refuses a
  direct run), `0010_schema.sql` … `0500_code_scope.sql` (each source body byte-identical inside `BEGIN; … COMMIT;`, then the
  source's name and sha256 recorded in `public.wts_schema_migrations`, so the export manifest and the restore drill see the
  same history as a `migrate.js` database) and `0501_platform_export_role.sql` (`ops/sql/backup-role.sql` + its grant).
- Every file opens its own transaction: the bodies use `SET LOCAL ROLE` / `SET LOCAL search_path`, which outside a transaction
  would silently create objects in the wrong schema with the wrong owner. An error aborts the file; nothing is half-applied.
  (If the platform's runner wraps each file in a transaction itself, the inner `BEGIN` only warns; the test runs both ways.)
- **Superuser-only statements.** The schema needs a login that can create roles (CREATEROLE) **including BYPASSRLS roles**
  (`wts_definer`, `wts_jobs`, `wts_backup`), and PostgreSQL 16+. `0000_platform_roles.sql` checks this first and fails with
  "wts platform migrations: the login … cannot create BYPASSRLS roles — nothing was applied" (or "cannot create roles"): the
  deploy is then not published and the database stays empty. **Fallback** if the platform login lacks a right: (a) a new source
  migration replacing the BYPASSRLS attribute with permissive policies `TO wts_definer` / `TO wts_jobs` (and `TO wts_backup`
  SELECT policies), generated into the folder like any other — written only if a deploy reports this; (b) if role switching at
  connection start-up is refused, `WTS_DB_ROLE_MODE=local` on the site (the self-test's `jobsRole` says `local`).
- Production path: with this dependency the platform applies the migrations, so the release workflow has no migrate job and no
  database credential; its verify job runs `node server/db/platform-migrations.js --check` and refuses a change to or removal
  of a file released under an earlier server tag, and the deploy job refuses unless that check passed — see RUNBOOK "3T",
  last note.

### Deviations from the plan (recorded in docs/ACCOUNTS-PLAN.md, Appendix B.4)

1. **One database login, separate roles kept by switching.** The platform hands out one login (the database owner); it cannot
   give `wts_api`, `wts_jobs` and `wts_support` their own credentials (D12). The roles, grants, `FORCE ROW LEVEL SECURITY` and
   the `wts_definer` functions are unchanged; instead every request transaction starts with `SET LOCAL ROLE wts_api`
   (`core/db.js`, transaction-scoped, so a pooled connection never keeps it), and the jobs, the export and the support scripts
   connect with the start-up role `wts_jobs` / `wts_backup` / `wts_support` (a login that is not a member cannot connect; where
   the endpoint refuses start-up settings, `WTS_DB_ROLE_MODE=local` switches role per transaction instead — `migrate --platform`
   probes which works). **What is lost (the full residual):** every function holds `NETLIFY_DB_URL`, the same value as the
   migration credential — the database owner with BYPASSRLS, inheriting `wts_owner` and `wts_definer`. The D12 / §13.3
   credential separation and the read-only property of the export role are therefore NOT enforced by credentials on this
   platform: SQL running on the site could `RESET ROLE`, `SET ROLE` to any wts_* role (the `wts_jobs` and `wts_backup`
   connections can switch back to the login or to `wts_owner`), or disable row-level security. The only barrier is that the code
   never builds SQL from input (tagged templates only; the role name is checked against `^wts_[a-z]+$`). `site/isolation.js`
   logs this as a standing `config: one-login database` warning in production, and a dedicated `WTS_DB_URL` / `WTS_JOBS_DB_URL`
   (go-live check, RUNBOOK "Security notes for this platform") takes precedence over `NETLIFY_DB_URL`. `db/migrate.js --platform` grants the
   roles to the login (owner and definer inherited, as a superuser migrator would act; the run-time roles SET only) and
   refuses to start unless the login can create roles and BYPASSRLS roles (`loginReport`). **Probe before go-live** (RUNBOOK
   step 7): if the platform login cannot create BYPASSRLS roles, the fallback is permissive policies `TO wts_definer` /
   `TO wts_jobs` instead of the BYPASSRLS attribute — a new migration, written only if the probe fails.
2. **Ownership changes need CREATE.** A non-superuser may give a function to `wts_definer` only while that role can create in
   the schema: 001, 002 and 040 lend `CREATE ON SCHEMA wts` to `wts_definer` around the ownership change and take it back
   (unreleased migrations; a superuser migrator sees no difference).
3. **Weekly export without a dump tool, sealed to a public key.** A function has no `pg_dump`, and `isolation.js` keeps every
   key that can READ an export off the functions site. The export there is a `COPY` of every table in one REPEATABLE READ,
   READ ONLY transaction as `wts_backup`, packed with the same manifest (row counts, audit digest, migrations, ledger and anchor
   objects, blob manifest) and sealed with an ephemeral X25519 key agreement to `WTS_BACKUP_PUBLIC_KEY` (format `WTSX2`). Only
   `WTS_BACKUP_PRIVATE_KEY` (offline, and on the drill machine) opens it; `ops/restore-drill.js` restores either format
   (`--from-store` reads the newest export). The export lives in the `wts-exports` store in the **same** region
   (`eu-central-1`; there is no other EU region for Blobs), not "another region": the owner downloads one export a month to
   offline storage (RUNBOOK §9) and the platform's own database backups add a second copy.
4. **Regions.** Functions in London (`lhr`, pinned in each function's config and set as the site region) need the credit-based Pro plan; on Personal they and the database run in the United States
   (Ohio) — an owner decision recorded in RUNBOOK step 1. Blobs have no London region: `eu-central-1` (Frankfurt).
5. **Previews.** A deploy preview of a site with a database gets a copy of the production data: deploy previews and branch
   deploys are off, agent runs are off (each gets a database branch seeded from production) and builds are stopped; releases come
   only from `server-v*` tags (`WTS_DEPLOY_COMMAND` = the pinned CLI); older deploys' permanent addresses refuse to run.
6. **Proxy signature through a build-time substitution.** Netlify sets request headers on a proxy rule only in `netlify.toml`,
   which cannot read variables; the main site's build writes the value into its (unpublished) `netlify.toml`. The original host
   travels as the fixed header `X-WTS-Host`, trusted only together with a valid signature. Unverified until the live check of
   RUNBOOK step 12.5: which client address the functions site sees behind the rewrite (`x-nf-client-connection-ip`; the LAST
   value of a list is used) and that a client-sent copy of that header is not trusted (a forged-header check).
7. **Client version.** `functions/projects.js` now reads a leading "v" ("v4.0", as the page sends `RELEASE_NOTES[0].ver`); before,
   such a header switched the 426 gate off.

## Provider sign-in open items (lead decisions, kept at the integration)

- **Provider sign-out link (§11.2)**: the blocking provider sign-out step gives text instructions only. A link needs a
  `signOutUrl` per provider in `core/oidc-providers.js` carried in `GET /auth/providers` (a contract change), or §11.2 is
  amended to accept the text.
- **Resend in the provider code step**: there is no "Send again" (the finish contract has no resend body). The step shows the
  "Didn't get the code?" help and a Close; a new code comes from a new provider start.
- **Finish dialog host**: the provider finish steps keep their own `#acct_oauth_dlg` (focus move, Tab trap, focus return; the
  blocking sign-out step ignores Escape). A done sign-in closes it and completes through WP-C1's `completeSignIn`, whose
  dialog asks the hand-over question; the `providerEmailDiffers` note reopens it afterwards.
- **Settled at the integration**: one audit hash — the `audit_chain` trigger of `002-core.sql` (every writer, also
  `support_retire_identities`, inserts an empty hash and the trigger chains it); the retire-client notices are queued by
  `ops/retire-client.js` with the jobs credential (`keys.system.seal('mail.to', …)`, the one outbox format) and sent by the
  daily job; the signing-key refetch limit is one fetch per provider per fixed 5-minute window across instances
  (`oidc_fetch_claim`) plus each instance's in-memory limit (§4.11).

## Operations (WP-OPS)

`RUNBOOK.md` is the operations handbook (owner's activation checklist, releases, alerts, kill switches, incidents, security
reset, key rotation and compromise, backups and restore, support). `site/` holds the functions-only site: `handler.js` (the
host adapter for `/api/v1/*`), `isolation.js` (preview isolation), `monitor.js` (access lines and the §13.6 alert table),
`adapters.js` (blob store and e-mail bindings), `objects-loader.js` (the one blob-store choice for the API, the weekly
export and the ledger replay), `backup.js` (weekly encrypted export and restore drill), `build.js`
(`server/dist`, one function in `dist/entry/`) and `site.json`. `ops/` adds `weekly-export.js`, `restore-drill.js`, `monitor-check.js`,
`call-daily.js` and `sql/backup-role.sql`; `ci/secret-scan.js` is the secret scan. The release workflow
`.github/workflows/server-release.yml` runs only on `server-v*` tags and skips its deploy steps until the owner adds their secrets
(migrations: the platform applies them; the workflow checks the generated folder read-only). The static site's allow-list is `prism-build/publish-site.js` (`--check`), the account-block digest
`prism-build/acct-hash.js`.
